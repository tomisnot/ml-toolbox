 # ML Toolbox 开发者指南
 
 本文件是接手 ML Toolbox 开发工作的主入口。它描述当前代码中的分层、数据模型、运行路径、可扩展点和验证方式。算法语义属于 ML Toolbox，操作者治理属于 ml_mecha 与 mecha；维护者应先确定改动属于哪一层，再选择文件和测试。
 
 ## 1. 项目定位
 
 ML Toolbox 是一个以实验事实为中心的机器学习工作台。它把一次实验拆成可引用的对象：
 
 - 数据集：输入数据、目标列、图结构、逐行负载和数据版本；
 - 处理管道：拟合规则、训练验证划分、步骤参数和管道指纹；
 - 方法：带参数描述、训练入口、预测入口、指标和图表能力的算法对象；
 - 运行：某个数据集、管道、方法、覆写参数和随机种子的执行事实；
 - 训练记录：逐步指标、资源使用、日志、checkpoint 和终态；
 - 任务：后台执行的调度状态、取消请求和结果引用；
 - 实验账本：把数据、运行、训练和产物关联起来的可查询索引。
 
 软件界面、命令行、MCP 和 AI 工具都应落到同一套领域动作上。不要在某个宿主里复制一份“简化训练流程”。
 
 ## 2. 分层架构
 
 ### 2.1 领域层：ml_toolbox
 
 领域层不依赖 mecha。它可以在纯 Python 进程中运行，也可以被 ML 的 GUI、命令和后台任务调用。
 
 | 目录 | 当前职责 |
 |---|---|
 | ml_toolbox/api.py | 对外稳定对象、会话、请求、运行快照和运行回执 |
 | ml_toolbox/core/dataset.py | 数据源解析、数据集身份、特征与目标视图 |
 | ml_toolbox/core/pipeline.py | 预处理步骤、拟合、变换、划分和诊断 |
 | ml_toolbox/core/registry.py | 数据步骤和方法的注册、查找与描述 |
 | ml_toolbox/core/runner.py | 训练/预测的统一运行边界 |
 | ml_toolbox/core/runs.py | 运行记录、状态、指标和结果持久化 |
 | ml_toolbox/core/resources.py | 设备、内存、并发和资源预算 |
 | ml_toolbox/core/persistence.py | JSON、数组、曲线和运行目录的读写 |
 | ml_toolbox/core/plot_spec.py | 与后端无关的图表规格 |
 | ml_toolbox/methods/base.py | 方法接口、参数规格和方法上下文 |
 | ml_toolbox/methods/*.py | 线性、核方法、近邻、聚类、异常、时序等方法 |
 | ml_toolbox/methods/neural/ | 网络契约、训练器、TensorBoard、checkpoint 和自定义网络 |
 | ml_toolbox/opt/ | 超参数空间、试验、优化器、并行执行与优化结果 |
 
 领域层可以抛出领域异常，但不要返回 mecha 的 ToolDefinition、Gate 或 MCP 类型。
 
 ### 2.2 适配层：ml_mecha
 
 ml_mecha 把领域动作接入 mecha，同时保持动作实现只有一个来源。
 
 | 文件 | 责任 |
 |---|---|
 | ml_mecha/commands.py | 命令名称、参数、作用、副作用和回执字段的唯一声明 |
 | ml_mecha/core_commands.py | 命令声明到执行函数的绑定、参数归一化和回执整理 |
 | ml_mecha/engine.py | MLEngine；协调数据、方法、运行、后台任务和项目账 |
 | ml_mecha/assembly.py | 创建软件实例、注册命令/查询/工具/Jobs/产物和监控 |
 | ml_mecha/tools.py | 将命令和查询投影为 AI 可调用工具，并控制回执大小 |
 | ml_mecha/validator.py | 数据、设备、资源规格和运行前置条件校验 |
 | ml_mecha/ledger.py | ML 运行账的身份索引与可重建记录 |
 | ml_mecha/summarizer.py | 面向监控的事件摘要 |
 | ml_mecha/job_logs.py | 后台任务 stdout/stderr 尾部缓冲 |
 | ml_mecha/runtime.py | 本地运行环境和路径初始化 |
 | ml_mecha/watch.py | 长任务的独立观察进程 |
 | ml_mecha/authority_read.py | 只读写权和控制面状态 |
 | ml_mecha/capabilities.py | 项目能力清单和参数投影 |
 
 适配层不实现算法。它负责把输入变成领域请求，把领域结果变成稳定回执，并把写入纳入 mecha 的操作关联。
 
 ### 2.3 宿主层
 
 app.py、app_entry.py、GUI、MCP host、mecha_site.py 和 dsh 资产只负责启动、展示和协议转换。宿主层可以选择默认视图和分页方式，不能改变运行语义。
 
 ## 3. 领域对象和生命周期
 
 ### 3.1 数据集
 
 prepare_dataset 接收 source、target、time_col、graph、payload 和 pipeline。source 可以是文件、进程内表格、数组或合成数据规格。数据集建立后得到 dataset_id；它代表内容和语义的组合，而不是一个随意名称。
 
 数据集包含以下信息：
 
 - 原始来源描述及安全归一化后的路径；
 - 行数、列名、dtype、缺失值和目标类型；
 - 特征列与目标列；
 - 训练、验证、测试划分策略和随机种子；
 - 图的节点/边索引及 edge_attr；
 - 逐行负载引用；
 - 预处理管道的 pipeline_id；
 - 数据集内容指纹和创建时间。
 
 大数组使用 payload 的 HDF5 或数组存储；命令回执只返回形状、字段和引用。不要把完整数组塞进命令回执或 AI 上下文。
 
 ### 3.2 处理管道
 
 Pipeline 是一组可拟合的步骤。典型步骤包括缺失值处理、类别编码、缩放、特征选择和划分。拟合只允许使用训练部分，避免验证或测试信息泄漏。
 
 一个步骤必须说明：
 
 - 稳定 key；
 - 参数规格和默认值；
 - fit 所需的输入；
 - transform 的输入输出形状；
 - 序列化形式；
 - 诊断信息（可选）。
 
 pipeline_id 由规范化的步骤和 split policy 共同决定。修改步骤参数会得到新的管道身份，不应覆盖已有运行的解释。
 
 ### 3.3 方法
 
 方法实现位于 ml_toolbox/methods。基础接口由 methods/base.py 定义，通常包括：
 
 - 方法名和描述；
 - 参数规格与类型；
 - fit 或 run；
 - predict 或 transform；
 - 指标方向与支持的问题类型；
 - 资源估算；
 - 诊断和图表规格。
 
 方法应接受已经准备好的数据视图。方法不能自行重新读取原始文件，也不能偷偷改变数据划分。需要缓存时使用运行上下文提供的目录。
 
 新增方法的最小路径：
 
 1. 在 methods 下实现方法类；
 2. 在方法注册表中登记稳定名称；
 3. 提供参数规格、问题类型和主指标；
 4. 增加一个小数据集运行测试；
 5. 让 describe_methods 能返回完整描述；
 6. 确认 run_method 和 run_method_batch 均能调用。
 
 ### 3.4 运行记录
 
 RunRecord 描述一次可复核的执行。关键字段包括：
 
 - run_id；
 - dataset_id、pipeline_id 和 method；
 - overrides、seed、device 和 resource_guard；
 - started_at、finished_at、状态和错误；
 - metrics、warnings、diagnostics；
 - prediction、plot、checkpoint 和日志的结果引用；
 - 方法版本和参数快照。
 
 运行的终态必须明确：completed、failed、cancelled 或 rejected。异常不能只写入日志而让调用方得到一个看似成功的空结果。
 
 ## 4. MLEngine 的职责
 
 MLEngine 是 ML 项目内部的协调器。它不是 mecha 的框架接口，也不要求所有项目复用。
 
 它负责：
 
 1. 解析数据集引用并选择当前数据；
 2. 调用 pipeline 拟合与变换；
 3. 查找方法并规范化 overrides；
 4. 建立 RunRecord 和运行目录；
 5. 调用 runner 或 neural trainer；
 6. 接收资源、进度、取消和日志上下文；
 7. 写入 ML ledger 与结果引用；
 8. 把领域结果转换成命令层需要的回执。
 
 MLEngine 不负责：
 
 - 决定 AI 是否能调用；
 - 选择写权模式；
 - 实现 MCP、GUI 或网页协议；
 - 维护 mecha 的通用 History；
 - 用框架级字段替代 ML 的实验字段。
 
 MLEngine 的调用入口应从 engine.py 和 core_commands.py 进入。不要从工具闭包直接调用散落的训练函数。
 
 ## 5. 命令面
 
 commands.py 是命令声明的单一来源。当前主要命令如下。
 
 | 命令 | 用途 | 写入 |
 |---|---|---|
 | prepare_dataset | 建立数据集和处理管道 | current.dataset_id、current.pipeline_id |
 | run_method | 运行一个注册方法 | current.method 等运行上下文 |
 | run_method_batch | 顺序运行多个方法并隔离失败 | 运行记录与方法上下文 |
 | compare_methods | 运行并生成可排序对比表 | 运行记录与比较摘要 |
 | run_custom | 执行调用方提供的 Network 定义 | 自定义运行记录、checkpoint |
 | submit_run | 把可运行规格放入后台任务 | job 记录 |
 | read_job | 读取任务状态、进度、日志尾和结果引用 | 无 |
 | cancel_run | 请求协作式取消 | 任务取消标记 |
 | describe_run | 读取单次运行摘要 | 无 |
 | describe_training | 读取训练曲线和诊断 | 无 |
 | checkpoint_detail | 读取 checkpoint 元数据 | 无 |
 | set_job_limit | 调整项目内并发名额 | 调度状态 |
 
 命令声明中的 reason 是审计用途的保留参数。它不改变领域算法参数，但会进入操作记录和监控摘要。
 
 命令处理必须遵守三点：
 
 - 参数校验先于昂贵计算；
 - 回执只返回小而有用的摘要，大结果给 result_ref；
 - 命令失败必须返回结构化 error、error_kind、error_hint 和 error_suggest（适用时）。
 
 ## 6. 同步和后台路径
 
 ### 6.1 同步路径
 
 同步调用的主路径是：
 
 ~~~text
 ToolHost/CLI/GUI
   -> CommandRegistry
   -> command handler
   -> MLEngine
   -> dataset/pipeline/method/runner
   -> RunRecord + ledger + result refs
   -> structured receipt
 ~~~
 
 同步路径适合准备数据、读取元数据、小规模方法和快速预览。同步调用也必须建立 run_id（纯查询除外），以便结果与审计关联。
 
 ### 6.2 后台路径
 
 submit_run 使用 mecha Jobs 注册任务。任务上下文提供：
 
 - cancel_requested；
 - progress 回调；
 - job_id；
 - 运行目录；
 - 日志捕获；
 - 可选的结果引用。
 
 MLEngine 负责项目并发限制、资源预算、checkpoint 和恢复语义；mecha 负责通用任务生命周期。read_job 会同时报告框架 state 和 queued 调度事实。state=running 不代表已经获得训练名额，queued=true 才表示仍在项目队列中。
 
 取消是协作式的。训练循环需要主动检查上下文；无法立即停止时，回执必须说明取消请求与最终状态的区别。
 
 ## 7. 自定义网络
 
 run_custom 允许调用方提供 code 或 code_path，二者必须二选一。代码定义 Network 契约，训练循环由系统管理。
 
 Network 至少实现：
 
 - build(n_in, n_out, *, nn)；
 - 可选 loss；
 - 可选 configure；
 - 可选 forward_step。
 
 run_custom 的关键参数：
 
 - dry_run：用真实数据做前向形状试跑；
 - batch_probes：指定试跑批大小；
 - warmup_steps：在正式训练前做少量反传；
 - checkpoint_every：按优化步保存 last.pt；
 - resume_from：从 checkpoint 继续；
 - overrides：epochs、batch、lr、val_split 等训练参数；
 - device：auto、cpu 或 cuda:0；
 - persist：是否写入实验存档。
 
 自定义代码读取 ctx 提供的 device、数据和输出目录。不要在代码里创建默认 CPU 张量再与 GPU 模型混算。dry_run 不反传、不计入正式实验；warmup_steps 才用于发现训练动态错误。
 
 checkpoint 的职责是恢复训练状态和保护长任务结果。它不改变原 run_id 的身份，也不把一次恢复自动当成相同实验；回执要带 resume_from 和新旧运行关联。
 
 ## 8. 账本和身份
 
 ML 的账本由三类事实组成：
 
 1. 数据身份：dataset_id、pipeline_id、内容指纹和来源规格；
 2. 运行事实：run_id、方法、参数、状态、指标、警告和资源；
 3. 产物索引：曲线、checkpoint、预测、图表、日志和结果引用。
 
 账本文件和运行目录位于项目配置的 ML 数据根下，默认使用 .ml-mecha 作为项目状态目录。具体路径由 runtime 和 assembly 计算，不应在业务代码里硬编码。
 
 写账顺序应保证：
 
 1. 生成稳定身份；
 2. 建立运行记录；
 3. 执行领域动作；
 4. 写终态和指标；
 5. 写产物引用；
 6. 发出命令和操作关联事件。
 
 任一步失败都要保留可诊断的终态。派生摘要可以重新计算；原始运行记录和指标不可用摘要覆盖。
 
 ## 9. 查询和 AI 投影
 
 只读信息进入 Surface 查询和专用 read 工具。工具层的主要原则是：
 
 - 使用 describe_methods 获取能力，而不是猜方法名；
 - 使用 describe_dataset、describe_run 和 describe_training 获取小摘要；
 - 通过 limit、offset、tags、pick 或 compare 选择字段；
 - 大曲线和文件只给引用或尾部；
 - 轮询 read_job 时默认返回最新进度和有限尾部；
 - 超时表示仍在运行，不等于失败；
 - cancel_run 的 terminal 字段表示请求前任务是否已经结束。
 
 run_queries 是只读查询组合入口。它可以一次执行多个查询并按 pick 返回字段，减少 AI 往返。任何带副作用的操作仍必须走命令，不得伪装成查询。
 
 工具描述应解释输入、输出和失败处理。不要把内部线程、数据库路径或 Python 对象暴露给调用方。
 
 ## 10. 资源和安全边界
 
 validator.py 负责在运行前检查：
 
 - 数据源是否存在且在允许根目录；
 - 行数、维度和 dtype 是否符合方法要求；
 - device 是否可用；
 - GPU/CPU/内存预算是否可接受；
 - batch、epochs、workers 是否在项目限制内；
 - code_path 是否在允许的代码根内；
 - checkpoint 和 resume 引用是否存在且匹配。
 
 验证的目标是尽早给出可操作错误，而不是增加重复门禁。真正的资源消耗仍需由 runner 和 Jobs 观察。不要把“通过 validator”解释成“运行一定成功”。
 
 ## 11. 新增能力的工作流
 
 ### 新增数据源
 
 1. 在 dataset.py 中定义 source kind；
 2. 完成安全路径解析和最小元数据读取；
 3. 统一转换为内部表格/数组/图视图；
 4. 更新 prepare_dataset 的 source 描述；
 5. 增加内容指纹和重复加载测试；
 6. 确认 payload 和大数组不会进入 JSON 回执。
 
 ### 新增预处理步骤
 
 1. 实现 fit/transform 和序列化；
 2. 在 registry 中注册 key；
 3. 声明参数和诊断字段；
 4. 确认只在训练部分拟合；
 5. 测试缺失值、空列和列顺序变化；
 6. 检查 pipeline_id 是否随参数正确变化。
 
 ### 新增算法方法
 
 按“方法对象—注册表—命令—查询—工具”顺序接入。算法参数留在 methods；命令只承载运行级 overrides。方法失败要保留 run_id 和结构化原因，使 batch/compare 能隔离失败。
 
 ### 新增只读能力
 
 查询函数应返回可序列化的小对象，包含身份、状态、字段说明和分页事实。注册到 assembly 的 Surface.QUERY，并在 tools.py 生成投影。查询不得写状态或触发隐式训练。
 
 ### 新增后台动作
 
 把同步实现写好后，再由 submit_run 包装。任务函数只接收 ExecutionContext 和规范化请求，终态统一由 engine/runner 落账。不要为后台路径复制一套算法实现。
 
 ## 12. 测试和验证
 
 常用检查：
 
 ~~~powershell
 python tests/test_ml_capabilities.py
 python tests/test_ml_mecha.py
 python tests/test_api.py
 python tests/test_process_contract.py
 python tests/test_resources.py
 python tests/test_pipeline_safety.py
 python tests/test_fitted_pipeline.py
 python tests/test_opt.py
 python tests/test_tensorboard.py
 python tests/test_regressions.py
 ~~~
 
 涉及工具投影时补充 test_ai_efficiency、test_manual_surface、test_authority_read 和 test_panel_web。涉及后台任务时补充 test_runs_limit、test_process_contract 和 test_control_endpoint。
 
 验证重点：
 
 - 命令声明与真实写入状态一致；
 - 同步和后台调用得到同一领域结果；
 - 失败有 run_id 或 job_id 可追踪；
 - 任务终态、取消和超时语义准确；
 - 长结果通过引用返回；
 - 自定义网络 dry_run 能抓出真实批次形状问题；
 - checkpoint 读写和恢复字段一致；
 - 数据集和管道身份在重复加载时稳定。
 
 ## 13. 维护边界
 
 - mecha 不提供 ML Engine；MLEngine 只属于本项目。
 - ml_mecha 不替代 domain runner，不在工具闭包里实现算法。
 - Job 的调度与生命周期由 mecha 提供，ML 决定并发、预算和 checkpoint。
 - 运行事实与派生摘要分开；摘要可以重建。
 - 取消不保证立即中断；最终状态以 read_job 和 run record 为准。
 - checkpoint 是训练保护机制，不是通用的任意代码恢复。
 - GPU、TensorBoard、HDF5、Optuna 等能力按可选依赖存在；调用方应从 capabilities 和回执判断可用性。
 - 运行目录、账本和产物路径由 assembly/runtime 决定；业务代码只使用提供的引用。
 
 ## 14. 接手任务的阅读顺序
 
 1. 先读本文件和 docs/使用指南.md；
 2. 读 ml_mecha/assembly.py，确认当前装配；
 3. 读 ml_mecha/commands.py，确认公开命令；
 4. 读 ml_mecha/engine.py 和 core_commands.py，确认动作路径；
 5. 按任务进入 ml_toolbox/core 或 methods；
 6. 涉及后台时读 tools.py、job_logs.py、watch.py；
 7. 先写一个领域层测试，再接工具和面板；
 8. 完成对应测试后再更新 capabilities 或用户文档。
 
 判断改动位置的简单规则：数据和算法放 ml_toolbox，运行协调放 MLEngine，治理和投影放 ml_mecha，展示放宿主层。若一个改动同时触及四层，应先画出输入、事实、产物和回执的流向，再开始编码。
