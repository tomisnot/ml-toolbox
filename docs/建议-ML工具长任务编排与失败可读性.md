# ML Toolbox 开发侧优化方向（使用体验与机制构想）

> 依据：本轮 NQS 项目**一整晚的连续使用**（数十次 `run_custom`/`submit_run`、
> 多次重启、多个 250–900 epoch 长训练、多份数据集、反复的 URL/会话中断）。
> **只谈使用体验与机制，不谈具体代码实现。**
>
> 先说已经好用的（见 §0），免得被读成整体否定。

---

## 0. 已经显著好用的（本轮实测）

| 能力 | 实测收益 |
|---|---|
| **`dry_run` + `warmup_steps`** | 形状错误从"约 15 个往返"降到 1–3 个；`verdict` 直接判发散 |
| **`code_path`** | 150 行网络代码只报路径，调参不重发 |
| **`read_job` 摘要 + `tail`** | 从"回全量上千条"变成 8 条 |
| **`describe_training` 的 `grad_layers` 摘要** | `latest` 里从 30+ 个梯度降到 6 个 |
| **结构化错误归因** | `bad_payload_hdf5` 那条（"负载 'phase' 第 0 维 474 vs 观测表 651 行"）**一次就指明了问题**，是全场最好的报错 |
| **失败给真原因** | `unknown_dataset` + "本会话已准备的数据集：（空）"—— 一眼看清 |

**结论：报错质量与观测面这两块，本轮的改进方向是对的，继续做。**

---

## 1. 一句话结论

> **当前最主要的摩擦不是"某个功能缺失"，而是"AI 作为编排者，无法有效地等待与追踪"。**
> 长任务全靠反复轮询 + 人工转达；失败了有时静默、有时报在假位置；
> 重启后身份（dataset_id / job_id）全部失效。
> **这三件事合起来，把"24 小时无人值守"变成了"人必须在旁边一遍遍说'跑完了'"。**

---

## 2. P0：卡住工作流的三件事

### 2.1 ⭐ 长任务没有"等待完成"原语（本用户直接点出的痛点）

**现象**：`read_job` 的 `wait_s` 上限 30 秒。要看一个 250–900 epoch 的训练，
只能反复轮询；用户的原话是"**不能靠我一遍遍告诉你跑完了**"。

**我实际付出的代价**：为等一个任务，我做了十几次轮询调用；后来改用本地
`pwsh` 睡 9.5 分钟再查目录——**这是绕过你的工具，说明缺了这个能力**。

**建议机制**（按推荐度）：

1. **完成事件（最优）**：任务终态时**主动向会话注入一条消息**，
   像 promise resolve。AI 完全不轮询，被唤醒即可。
   - 形态：`submit_run(..., notify_on="terminal")`
   - 这样"等待"不再是 AI 的负担，而是框架的职责。
2. **阻塞等待（次优，但立刻可用）**：`read_job(job_id, wait="terminal", timeout_s=3600)`
   —— 允许一次阻塞到终态，而不是 30 秒上限。
3. **队列式轮询**：`wait_any(job_ids, timeout_s=…)` 返回**第一个**完成的任务。
   适合"一把投多个、谁先完谁先报"。

### 2.2 失败有时静默、有时报在假位置

本轮遇到四种"报错不可用"：

| 现象 | 我实际看到的 | 应该是 |
|---|---|---|
| 显存不足 | `CUDA error: device-side assert triggered`，栈指向 `set_probe` | "**显存不足**：(R,K,L)=… 需约 X GB，可用 Y GB ⇒ 减批次或让网络分块" |
| CUDA 上下文毒化 | 之后**每个**任务都在第一次同步处报同一个错 | "本进程 CUDA 上下文已毒化，**重启前所有 CUDA 运行都会报假错**"——**且这条要置顶**，不要放在 `hint` 末尾 |
| `dataset_id` 失效 | `state:"done"`、`error:""`、无 run、无日志 | ✅ 已修为 `unknown_dataset`（好） |
| 并发提交 | `未注册的方法: custom_network`（可用方法表里躺着 59 个经典方法）| 见 §2.3 |

**建议机制**：
- **失败必须至少有一个非空字段说明"是哪一类"**（哪怕就一个 `kind`）。
  `state=done && error=="" && run_id==""` 这个组合**不应该存在**——它无法区分
  "成功但慢"和"从未启动"。
- **显存不足应作为一等错误**（见 §3.3），不要落到 CUDA 层去报。

### 2.3 提交竞态：并发/取消后提交会失败

**现象（实测）**：连续 `submit_run` 三个 `run_custom`：

```
第 1 个 → 成功
紧接的第 2、3 个 → 全部 state=done，error:
  invalid request: "未注册的方法: custom_network"
```

**取消一个任务后立刻提交**，也复现同一错误。等一会儿再投就成功。
⇒ 看起来是"自定义网络"这个方法**在每次提交时被临时注册**，存在注册竞态。

**建议机制**：
- **会话启动时一次性注册** `run_custom`，而不是每次提交现注册；
- 或者**框架内部把提交串行化**，让调用方无需知道这个约束。
- **兜底**：报错要能自解释——"自定义网络方法尚未就绪，请重试"，
  而不是把 59 个可用方法列一遍（那反而误导，让人以为方法名写错了）。

## 3. P1：效率与可靠性

### 3.1 作业身份不持久（"job 名占位"问题）

**现象**：`job-1` / `job-2` 只是**会话内计数器**。重启后 `job-1` 指向完全不同的任务；
我就曾拿旧 `job-1` 去读，拿到的是别的 run。没有稳定身份，也就无法：
把 job ↔ run ↔ dataset ↔ 判据 串起来；重启后继续追踪。

**建议机制**：
- **可读且稳定的名字**：`submit_run(name=…)` 里的 `name` 应当**全局唯一、可作为句柄**
  （现在它只用于存档，查询仍必须用 `job_id`）；
- **`read_job` 接受 `run_id` / `name`**，而不只是会话内 `job_id`；
- **作业登记表（registry）落盘**：重启后仍能列出"我提交过什么、状态如何"。
  这直接决定"中断后能否自愈"。

### 3.2 作业上限 + 无队列

**现象**：上限 4 个并发（`MLTB_MAX_JOBS`）。超出直接**报错**，
而不是**排队**。我因此必须"投一个、等一个、再投一个"。

**建议机制**：
- **超出上限 → 入队**，有空位自动开跑（对"一次排满 24 小时"是刚需）；
- 上限调整**不需要重启**（重启会清空 dataset 与会话态，代价很大）。

### 3.3 缺显存预检

**现象**：6 GB 卡上，我的配置峰值 5.30 GB；运行时只 3.6 GB 可用 ⇒ OOM，
且被报成 device assert（§2.2）。**我事前完全不知道会不够。**

**建议机制**：
- 提交前给出**估算**："该配置预计峰值约 X GB，当前可用 Y GB"；
- 若明显不足，**立刻以可读错误拒绝**，而不是进 CUDA 层；
- 顺带：**自动分块应当是框架职责**——我为了不 OOM，在**自己的网络代码里**
  手写了 `forward_step`/`metrics` 的内部分块（按 R 切块、按块加权累加梯度）。
  这是通用需求（"大数据负载 + 小显存"），不该每个用户各写一遍。
  建议：**框架在 R 超过阈值时自动分块**，并在回执里说明"已分 N 块"。

### 3.4 数据集登记不持久、不幂等

**现象**：重启后 `dataset_id` 全失效，**必须重新 `prepare_dataset`**。
本轮我因此重复登记了七八次。更麻烦的是：每次登记**返回新 id**，
于是"上一轮用的哪份数据"在会话里丢失，只能靠我的记忆对齐。

**建议机制**：
- **以负载指纹为主键**：同样的 `source`+`pipeline` ⇒ **返回同一个 id**（幂等）；
- 登记表**落盘**，重启后按指纹自动复原；
- 并在 `read_job` / `describe_training` 回执里**回显 dataset 的指纹**，
  这样"这次跑的是哪份数据"永远可查。

### 3.5 声明式链（"跑完 A 再跑 B"）

**现象**：我现在是**人肉编排**——投 A、轮询、投 B、轮询……中间任何一步断了（会话
中断、竞态失败）链条就断。用户要的"24 小时无人值守"其实需要**框架侧**支持。

**建议机制**：
```
submit_chain(steps=[
  {name:"k25", code_path:"net.py", dataset:"…", overrides:{…}},
  {name:"k60", code_path:"net.py", dataset:"…", overrides:{…}},
  {name:"k100", …}
], on_failure="continue")     # 或 "stop"
```
- 每个 step 独立落盘；
- 失败可配 `continue`/`stop`/`retry(n)`；
- **配合 §2.1 的完成事件**，AI 只需声明一次。

## 4. P2：体验细节

| # | 现象 | 建议 |
|---|---|---|
| 4.1 | `warmup_steps` 的 `verdict` 说"✅ 40 步内在下降"，但我实测**同类发散发生在 step 120** | `verdict` 明示"**N 步内**健康，不代表 N 步之后健康"，并建议窗口覆盖"损失分段切换"那一步；或自动延长到平台期 |
| 4.2 | 无 ETA / 吞吐反馈 | 回执带 `epochs_per_s` 与 ETA（我从 `progress` 自己算的） |
| 4.3 | `read_job` 的 `progress` 仍是数组 | 已有 `tail`，可再进一步：只回 `progress_latest` + 里程碑（25%/50%/75%） |
| 4.4 | 重启是"万灵药"但代价大（清 dataset/job） | 把"需要重启"与"不需要重启"的修复分开标注；能热修的尽量热修 |

## 5. 一个更高层的建议：运行清单（run manifest）

把上面几条串成一个机制：**每个项目一份落盘的运行清单**，记录

```
数据集（按指纹） → 负载（文件+行数） → 作业（稳定名） → run_id → 判据与结果
```

好处：
- **重启即可复原**：不必重新登记、不必靠记忆对齐；
- **可审计**：任意一个 run 都能追到"用了哪份数据、什么参数、判据是什么"；
- **可续跑**：中断后知道"链子进行到哪一步了"；
- 对 AI 尤其重要：**跨会话的连续性**不该依赖对话上下文的记忆。

---

## 6. 优先级建议（如果只做三件）

1. **完成事件 / 阻塞等待**（§2.1）——直接消除"用户一遍遍说跑完了"；
2. **失败永不静默、且报真因**（§2.2）——OOM 与上下文毒化必须可读；
3. **作业登记表落盘 + 稳定身份**（§3.1/§3.4）——让重启不再清零。

这三件做完，"24 小时无人值守"才真正成立：**AI 声明一次 → 框架排队执行 →
完成时唤醒 AI → 失败可读可续**。
