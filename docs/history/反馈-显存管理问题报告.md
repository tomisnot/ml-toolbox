# 反馈：显存管理问题报告（AI 侧实跑后登记）

> **谁写的**：用 ML Toolbox 训练神经网络波函数（NQS/长程 XY 蒸馏）的**使用者（AI 操作）**。
> **写给谁**：ML Toolbox 的开发者。
> **怎么来的**：不是读代码推断——是**真的把训练跑到 OOM 与崩溃**，然后用
> ① PyTorch 分配器自省（`memory_allocated / reserved / max_memory_allocated / mem_get_info`）、
> ② Windows 性能计数器（按进程的专用/共享显存）、③ 源码取证 三条线交叉定位。
> 期间**三次训练在同一处崩溃**，且框架没给栈（见问题 5），排查成本很高。
>
> **一句话**：在"输出维度随行数增长的模型 + 大 payload"这一组合下，框架有三处会把显存
> 顶到远高于实际需求（实测 `allocated 1.29 GB` 而 `reserved 5.83 GB`、峰值 **8.94 GB** 于 **6 GB** 卡），
> 表现为"第一轮勉强够、第二轮溢出共享内存、速度腰斩"，并暴露出一个**必崩**的探针采集约定。

## 1. 摘要

| # | 问题 | 位置 | 严重度 | 触发现象 |
|---|---|---|---|---|
| 1 | **整份 payload 常驻显存** | `methods/neural/trainer.py:696` | 高（大数据集） | 显存被负载长期占住，与模型规模无关地抬高基线 |
| 2 | **验证不分批**（整份验证集一次前向） | `trainer.py:827-831` | 高 | 单次物化 ~5 份 `(R, M)` ⇒ 峰值 8.94 GB、溢出共享内存、速度腰斩 |
| 3 | **探针采集假定"单次前向"** | `recorder.py:107-113, 201-230` | 高（会崩） | 任何**分块实现**的 `forward_step` 必崩 `IndexError: index 8 is out of bounds for axis 0 with size 8` |
| 4 | 探针行数固定 256（无显存预算） | `custom.py:376` | 中 | 大 payload 时单笔探针前向 ~1 GB，且**不可分块**（受问题 3 约束） |
| 5 | **失败处理丢弃栈** | `custom.py:463-471` | 中（可调试性） | hint 说"栈留在宿主日志"，**实测没有**；`import traceback` 是死代码 |
| 6 | Windows 不支持 `expandable_segments` | 平台 | 信息（非 bug） | 碎片无法自愈，只能靠主动归还；影响"reserved 远大于 allocated"的预期 |
| 7 | 测量面误导：Windows 计数器的"共享显存"是承诺口径 | 平台/文档 | 低（但会带偏判断） | 计数器报 7.3 GB 共享，而 PyTorch 实际只用 1.7 GB |

## 2. 环境与复现

- 机器：Windows，单卡 **RTX 4050 Laptop 6141 MiB**（桌面合成器 `dwm` 另占 ~1.9 GB、`NVIDIA Overlay` 0.4 GB
  ⇒ **训练实际可用 ~3.6 GB**）；主机内存 15.8 GB。
- 软件：`torch 2.7.1+cu128`；ML Toolbox 经 MCP 使用（`run_custom` + `prepare_dataset` + `submit_run`）。
- 复现用的两个数据集（都在本机，形状如下）：

| 数据集 | 行数 | 单行载荷 | `supp_re` 张量 |
|---|---|---|---|
| `xy_mix_ladder16` | 5000 | `xr(16,6)`、`edge_attr(16,16,6)`、`emask(16,16)`、`supp_re(65536)`、`n_sites()` | **1.31 GB** |
| `xy_mix_big` | 200 | 同上但 `n=20`：`supp_re(1048576)` | **0.84 GB** |

- 复现命令（最小）：`prepare_dataset(payload={"hdf5": {...}})` → `submit_run(code_path=…,
  overrides={"batch":8,"epochs":1,"val_split":0.2}, checkpoint_every=250)`；
  网络代码只需实现 `forward_step`，其返回 `(out, target)` 的 `out` 形如 `(R, 2^n)`。
- 观测手段：在网络代码里打印
  `torch.cuda.memory_allocated/reserved/max_memory_allocated()` 与 `torch.cuda.mem_get_info()`。

## 3. 逐问题取证

### 问题 1【高】整份 payload 常驻显存

**位置**：`ml_toolbox/methods/neural/trainer.py:693-696`
```python
    #: 逐行负载的**张量版**：整份放在设备上，按批索引 ⇒ 每批只切一次（省拷贝）。
    pay_t = None
    if payload:
        pay_t = {str(k): _as_tensor(v, torch, dev) for k, v in payload.items()}
```

**实测**：`supp_re`（5000×65536，float32）= **1.31 GB** 从训练开头占到结尾；
训练步的 `allocated` 常年在 1.29~1.67 GB —— **几乎全是这份负载**，模型本身只有 44 万参数。

**影响**：负载规模直接决定显存下限，与模型/批大小无关。n_max=20 时每行 4.19 MB，
**850 行就等于 3.5 GB** —— 在 6 GB 卡上还没开始算就已经注定溢出。
注释里"省拷贝"是合理的动机，但它把"省拷贝"和"省显存"绑成了一个不可选项。

**建议**：把"整份上卡"改成**可判定的策略**：payload 字节 ≤ 空闲显存×某比例时保持现状（快），
否则留 CPU、逐批 `to(dev, non_blocking=True)`。若要保护用户代码的行为一致性，
可加显式开关 + 在 `ctx` 里暴露 `payload_device` 让用户可判。

### 问题 2【高】验证不分批（整份验证集一次前向）

**位置**：`trainer.py:819-838`
```python
                        vi = torch.tensor(np.asarray(va, dtype=np.int64), dtype=torch.long)
                        with hook_device(torch, dev):
                            vo, vt = forward_step(model, (Xva, yva if has_y else None),
                                                  _ctx(vi, ep, kind="val"))
                        vl = float(loss_fn(vo, vt))
```

**实测（同一 run、同一步号的对照）**：

| 时刻 | `allocated` | `reserved` | `max_memory_allocated` | `gpu_free` |
|---|---|---|---|---|
| step 200（训练中） | 1.31 GB | 5.83 GB | 1.64 GB | **0.00 / 6.00 GB** |
| step 1000（跨过一次轮末） | 1.67 GB | 6.28 GB | **4.60 GB** | **0.00 / 6.00 GB** |

一次更早的运行里 PyTorch 直接报出 OOM：
```
OutOfMemoryError: CUDA out of memory. Tried to allocate 1.46 GiB.
GPU 0 has a total capacity of 6.00 GiB of which 0 bytes is free.
Of the allocated memory 7.34 GiB is allocated by PyTorch, and 3.98 GiB is reserved
by PyTorch but unallocated.
```

**机理**：我们的能量是 `(R, 2^16)`；框架一次把整个验证集（示例中 750 行）交给 `forward_step`，
于是 `E / log_softmax / pe / exp / sqrt` **约 5 份 `(R, M)` 同时存活**（≈2.4 GB 单笔），
叠加常驻负载（问题 1）与分配器碎片 ⇒ 峰值 8.94 GB。

**影响面（谁都会踩）**：任何"输出维度 = 行数 × 输出宽度、且宽度较大"的自定义模型
（NQS 的 2^N 构型、大词表、逐像素输出）。用户被迫在自己的 `forward_step` 里分块——
而**分块正好踩问题 3**（这就是我们三次崩溃的因果链）。

**建议**：框架侧按 `batch`（或 `ctx['chunks']`）分批求验证损失，再按行数加权平均。
语义上是等价的：训练循环本身用 `tot + loss·len(xb)`，即约定 `loss_fn` 返回**批内逐行均值**。

### 问题 3【高】探针采集假定"单次前向"，分块实现必崩

**位置**：`ml_toolbox/methods/neural/recorder.py`

```python
# :107-113  采集（覆盖式）
    def _relu_hook(self, module, inputs, output):
        if self._capture:
            self._relu_activations.append(output.detach())

    def _latent_hook(self, module, inputs, output):
        if self._capture:
            self._latent_features = output.detach()          # ← 每次调用覆盖前一次

# :226-230 使用（按探针 X 的行数算下标）
            latent = self._latent_features
            if latent is None:
                return None
            arr = latent.cpu().numpy()
            return arr[self._probe_selection]                # ← 行数不匹配就 IndexError
```

**实测崩溃（三次训练同一处）**：
```
[tb] trainer.train 抛异常: IndexError('index 8 is out of bounds for axis 0 with size 8')
Traceback (most recent call last):
  File ".../trainer.py", line 874, in train
    recorder.epoch(ep, train_loss, vl, cur_lr, extra=extra, ...)
  File ".../recorder.py", line 167, in epoch
    latent = self._collect_probe()
  File ".../recorder.py", line 230, in _collect_probe
    return arr[self._probe_selection]
IndexError: index 8 is out of bounds for axis 0 with size 8
```
（栈是我们在网络代码里**自己包了一层 `trainer.train`** 才拿到的，见问题 5。）

**机理**：探针固定喂 256 行（`custom.py:376`），`_probe_selection` 按 256 行生成；
若 `forward_step` 内部分块（例如 32×8 行），`_latent_hook` **只保留最后一次**（8 行），
`arr[sel]` 里 `sel` 含 8 ⇒ 越界。**这不是用户的 bug，是采集契约没写出来。**

**附带（同一处的第二个隐问题）**：`_relu_activations` 是**扁平列表**，
`_collect_probe` 用 `zip(self._relu_linear, vals)` 与模块对齐（`:222-225`）。
分块后列表顺序变成 `[chunk0.m1, chunk0.m2, …, chunk1.m1, …]` ⇒ **模块与激活错位**，
死 ReLU 指标（`dead_relu` / `layers/health`）会**静默算错**。

**建议**：采集改成**按模块名分桶、每桶收多段**，在 `_collect_probe` 里沿 dim0 拼接；
`sel` 从**拼接后的真实行数**推导而不是从探针 X 行数推导；实际采到多少行进诊断。

### 问题 4【中】探针行数固定 256，无显存预算

**位置**：`custom.py:376`
```python
        probe_rows = prep.tr_idx[:min(256, len(prep.tr_idx))]
```
**实测**：n=20 时单行 `supp_re` = 4.19 MB ⇒ 探针一次前向的输出 `(256, 2^20)` = **1.07 GB**；
又因问题 3 的约束**不能分块**，它是轮末最大的单笔瞬时开销。

**建议**：按"单行字节 × 预算"自适应（如 ≤256 MB），或允许从 `resource_guard` 覆盖。

### 问题 5【中】失败处理丢弃栈，且提示与事实不符

**位置**：`custom.py:463-471`
```python
        except Exception as exc:                             # noqa: BLE001
            import traceback                                  # ← 引入了但**从未使用**
            res = self._new_result(target_kind=kind, params={"lr": lr}).fail(
                f"自定义网络训练失败：{type(exc).__name__}: {exc}",
                kind="network_runtime_error",
                hint=_device_error_hint(exc) or
                     "是你那段网络代码在训练期抛的（不是框架）；栈留在宿主日志",
                suggest="改代码后重跑；`describe_network` 可取回上一次的源码对照")
            return res
```
**实测**：宿主日志（`_mecha_runtime/logs/ML.log`）里**只有消息、没有栈**；
`read_job` 在失败时也不回 `logs_tail`。⇒ 三次崩溃全靠"在用户侧包一层 `trainer.train`"才定位。

**建议**：`logging.exception(...)` + 把 `traceback.format_exc(limit=N)` 写进诊断/回执，
并把 hint 文案改成与事实一致（或删掉"栈留在宿主日志"这半句）。

### 问题 6 & 7【信息】平台与测量面

- **`expandable_segments` 在 Windows 不支持**（PyTorch 原文）：
  `UserWarning: expandable_segments not supported on this platform`。
  ⇒ OOM 报错里那条"建议设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`"
  **在 Windows 上无效**；碎片只能靠主动归还（`torch.cuda.empty_cache()`）缓解。
- **Windows 计数器口径会带偏判断**：按进程的 `GPU Process Memory\Shared Usage` 报
  pythonw 占 **6478 MB 共享 + 5305 MB 专用**，而同一时刻 PyTorch 自报
  `allocated 1.29 GB / reserved 1.69 GB`。该计数器更像**承诺/高水位**，不是实时占用。
  ⇒ 判断显存问题应以 **PyTorch 分配器自省**为准（另：`max_memory_allocated` 是
  **进程生命周期**的峰值，同一脊椎进程里连续跑多个 run 时会混入历史，判读前需
  `reset_peak_memory_stats()`）。

## 4. 我们这边的规避（不改框架也能跑；供参考）

| 规避 | 针对 | 代价 |
|---|---|---|
| 只在 `kind=='val'` 时在自己的 `forward_step` 里分块 | 问题 2 | 用户侧被迫写分块逻辑；且必须知道**探针不能分块**（问题 3） |
| 探针路径跳过 `pe/fid/ce`，只返回 `E` | 问题 4 | 需要知道"探针返回值不参与损失"（`custom.py:397` 丢弃 `_tgt`） |
| `build()` 与**每 200 步** `torch.cuda.empty_cache()` | 问题 6 | 周期性同步开销（可忽略） |
| `build()` 里 `reset_peak_memory_stats()` | 问题 7 | 无 |
| 网络侧包一层 `trainer.train` 打印栈 | 问题 5 | 无（但每个使用者都得自己发明一次） |

**效果**（同数据同一步号）：`reserved` **5.83 → 1.33 GB**、`gpu_free` **0.00 → 3.60 GB**、
单轮 **5.7 → 2.4 min**。

## 5. 影响面小结（谁会踩）

| 用户类型 | 会踩 |
|---|---|
| 输出维度随行数增长（NQS / 大词表 / 逐像素） | 问题 2（必踩）；若自己分块 ⇒ 问题 3（必崩） |
| payload 大（长序列、大构型空间） | 问题 1、问题 4 |
| `val_split` 大或验证集大 | 问题 2 加剧 |
| 任何训练失败的人 | 问题 5（拿不到栈） |
| Windows 用户 | 问题 6、问题 7 |
