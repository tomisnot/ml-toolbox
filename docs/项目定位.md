## 一、项目定位

**一句话**：一个可被多个项目复用的机器学习工具箱桌面软件——把"哪个方法好用"
这件无法提前预测的事，变成"在统一界面里低成本遍历尝试"的工程流程。

### 是什么

- **方法试验台**：面向一个具体数据问题，快速挂载、运行、对比多种机器学习方法
  （经典 sklearn 族、梯度提升族、神经网络族、降维/聚类等），直到找到合适的为止。
- **可调用组件**：工具箱的核心逻辑（数据处理、方法封装、评估）以 Python 库形式
  存在，GUI 只是其中一层壳；其他项目可以直接 `import` 调用，不强制走界面。
- **数据与实验的共享中枢**：同一份数据、同一套预处理、同一份实验记录，被所有
  方法共用，避免每个项目重复造轮子。

### 不是什么

- 不是 AutoML 框架——不做自动搜索最优模型的黑箱承诺，核心是**人工可检视的遍历**，
  每个方法的中间过程与图都摊开给人看；
- 不是 Notebook 的替代品——面向"重复出现的工程场景"，不是一次性探索脚本；
- 不是 Web 应用——桌面端（PyQt5），单机、离线可用、无服务依赖。

## 二、核心目标

按优先级排序，前两条是用户明确提出的突出特点。

### G1. 全面：方法可遍历

- 建立**统一方法接口 + 注册表**：任何方法实现同一契约（fit / predict / 评估指标 /
  核心图声明）即可注册进工具箱，被遍历系统自动发现。
- 支持**批量对比运行**：同一数据、同一划分下一次跑多个方法，产出横向对比视图
  （指标表 + 各方法核心图并排）。
- 方法覆盖按"场景族"组织：回归、分类、聚类、降维、时序、异常检测等，每族内
  从简单到复杂梯度覆盖；方法数量随需求持续扩充，扩充成本必须趋近于零
  （新增一个方法 = 实现一个类 + 声明一张核心图，不改主框架）。

### G2. 可视化管理与检视：UI 基类高自由度

- **每个方法的核心图不一样**是本项目 UI 的根本约束。UI 基类不预设"图长什么样"，
  只预设"检视页的结构"：方法以插件形式声明自己的检视页（画布类型、分页、
  可调旋钮的位置），基类负责装配。
- 复用已验证的 UI 模式（见 `UI design/ui_patterns.md`）：
  - **处理链分页**：数据流每一步（加载→清洗→特征→划分→训练→评估）各占一页，
    每页回答一个问题；
  - **旋钮放在语义位置 + 就地重跑**：调参控件放在它影响的图旁边，配
    "⟳ 应用并重跑"，参数空 = 默认、覆写仅本次运行生效；
  - **大卡片模式**：每个流程步骤一张全宽卡片，右侧大号关键数字（样本数、维度、
    分数），辅助表格退居底部；
  - **自适应刻度**：大数据量图形（特征相关热图、混淆矩阵等）用 pyqtgraph，
    缩放随动标注，几千维不卡；
  - **零侵入诊断开关**：`diag=False` 默认零开销，开启后中间产物装进结构化 dict
    供 UI 消费，UI 对缺失诊断数据显示语义化占位提示；
  - **导出兜底**：每个数据面板配导出按钮（npz/csv/json），UI 覆盖不了的分析
    需求交给导出。

### G3. 统一的数据处理与管理

- **单一数据入口**：所有方法消费同一份数据集对象（含原始表、特征矩阵、缺失值
  标记、划分方案），方法层不允许各自偷偷读文件。
- **预处理管道可复用、可检视**：清洗/编码/缩放/特征构造以有向步骤链表达，
  每一步的输入输出维数、样本数、关键统计量都在"处理链"页可见（对应模式 4
  的大卡片摘要）。
- **实验记录持久化**：每次运行 = 数据快照 + 管道版本 + 方法 + 参数 + 指标 +
  核心图存档，可恢复、可对比、可复现。

## 三、基本原则

### P1. 核心逻辑与界面分离

方法封装、数据处理、评估全部是可独立 import 的纯 Python 模块，GUI 通过信号/
契约消费它们。判据：不开 GUI 也能用工具箱完成全部工作。

### P2. 契约优先，注册扩展

框架与方法之间只通过稳定契约（数据对象、方法接口、诊断 dict、检视页声明）
交互。新增方法、新增图类型、新增数据格式都走注册，不改框架代码。

### P3. 零侵入默认，诊断可选

任何为"可检视性"付出的代价默认关闭：诊断开关不改变数值路径，覆写参数走
kwargs 运行级生效、不污染全局（对应 `UI design/pitfalls.md` #17）。

### P4. 视觉质量与功能同等重要

UI 每轮交付必须走截图自查闭环（`UI design/SKILL.md`）：
改代码 → 离屏渲染真实界面 → 截图 → 按 `checklist.md` 逐项自查（排版关 →
功能关 → 回归关）→ 修复重截。新踩的坑记入项目自己的 pitfalls 清单。
离屏渲染三铁律（CJK 字体、import 顺序、同步绘制）从第一天起写进截图脚本。

### P5. 遍历的边际成本持续下降

衡量工具箱好坏的唯一硬指标：**"再试一个方法"要花多少时间**。每次迭代都应
让这件事更快，而不是更重。

### P6. 技术选型锁定（现阶段）

- 语言/框架：Python 3 + PyQt5；
- 绘图：pyqtgraph（大数据量交互图，如热图/散点/曲线缩放）+
  matplotlib（静态图、出版质量导出），各按其长；
- 方法底座：优先封装成熟库（sklearn / xgboost / lightgbm / torch 等），
  工具箱只做统一封装与可视化，不重造算法轮子；
- 平台：Windows 优先（字体路径、离屏截图脚本均按此验证）。

### P7. 文档随代码走

契约（方法接口、诊断 dict 结构、检视页声明格式）以文档形式先行定义在
`docs/`，实现向文档对齐；偏离文档的改动需先更新文档。

### 实战验证结论（数学建模基准，`benchmarks/`）

工具箱"遍历好不好使"已用经典数模题型检验，结果落在已知答案附近：
Iris 分类 LDA f1=1.0、Housing 回归 LightGBM 居首、AirPassengers 时序
Holt-Winters rmse=5.6 显著优于朴素法 31.8——**证明统一遍历能自动逼近最优方法**。
LOF 在整簇平移异常上失效（auc=0.23）是其真实局限，不是 bug（见 pitfalls L8）。

### 宏观架构审视（v0.4.0 后一次体检，见 `docs/架构审视与改造建议.md`）

结论：P1/P8/P10/P13 等关键原则**经受住检验**；但发现一个系统性坏模式——
**契约被声明却无消费者**（`PageSpec.builder`、`kind="cards"`、
`Optimizer.inspect_pages`、`Objective.noise`、`InfeasiblePoint`、
`requires_numeric`)——以及"越小越好"指标集**三份且已分叉**、
`opt` 与 `core` 的 registry/persistence **复制内核**、
`core → methods` 的顶层 import 污染依赖闭包、并行度硬编码不可控。

改造提案 C1-C9 与执行批次、验收命令、文档同步清单见该文档；
其中 **C5（并行度契约化）** 与 **C4-4/4-5（noise 与 InfeasiblePoint）**
属真实缺陷修复，建议优先。
