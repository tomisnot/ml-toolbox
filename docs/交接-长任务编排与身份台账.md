## 4. 反馈通道专项分析（**先读这一节，它决定 R24 的实现形态**）

### 4.1 事实（我查证过的）

1. **MCP 面是拉取式**：`mecha` 里没有 notification / sampling / elicit 能力
   ⇒ **MCP 服务器无法主动把消息送进会话**。
2. **但 dsh 有注入通道**：本会话里我**收到过**两条不是我调工具拿到的消息 ——
   `background job pwsh-54 … finished [status: completed]…` 与 skill 目录变更的
   `system-reminder`。⇒ "向会话注入消息"这件事，**harness 层做得到**。
3. **我们已经在 dsh 内部有落脚点**：本仓 `dsh/` 是一个 **Cordis 插件**，两半：
   - **host 半** `dsh/src/index.ts`：能 `ctx.webServer.register({kind:'exact', path, handler})`
     注册 HTTP 路由（现在只用来把监控端点地址交给 client 半）；
   - **client 半** `dsh/src/client/index.ts`、`extraPages.ts`、`buttons.tsx`：
     跑在 dsh 界面（浏览器）里，能加页/加按钮；`launcher.py` 会生成 overlay 挂载它。
   - 另有 `dsh/README.md`（11 KB）说明纪律与自愈桥的适用条件 —— **先读它**。
4. `launcher.py` 已经：等权威就绪（探活 `/mcp`）→ 生成 `runtime/dsh-ml-mcp.patch.yml`
   → 起 dsh，并用 `MLTB_ML_ROOT` 告诉插件数据根在哪。
5. **只读监控面已经够用**：权威自带 `/latest`、`/series`、**`/runs`**、`/summary`、`/dashboard`
   （`ml_mecha/monitor_http.py`）⇒ 反馈通道**不必新造服务**，加一个"**阻塞到终态**"的
   端点（如 `/watch?handle=…&timeout=…`）即可，两条路径（C 与 A）共用它。

### 4.2 三条可行路径（按"省不省"排序）

| 路径 | 形态 | 每次长训练的**工具调用数** | 依赖 | 状态 |
|---|---|---|---|---|
| **A. 插件 client 半注入会话消息** | 面板/插件轮询权威的"作业终态"端点 ⇒ 往**会话里注入一条消息**（如同 harness 的 job 完成通知） | **1**（提交）+ 0（被唤醒）+ 1（可选读详情） | 需确认 dsh 的"注入消息"API 能不能被插件调用 | **最优，待验证** |
| **B. 插件 host 半 / dsh 侧订阅** | host 半或 dsh 自身订阅我们的 SSE/长轮询，直接触发 A | 同上 | 需 dsh 提供会话/调度 API | 与 A 同族，取其一 |
| **C. AI 侧 watcher（今天就能用）** | 我们提供一个**阻塞到终态**的入口（CLI 或 HTTP 长轮询，如 `python -m ml_mecha.watch <句柄>`）；AI 用**它自己的** `pwsh run_in_background` 起它 ⇒ **harness 会在它结束时注入通知** | **3**（提交 + 起 watcher + 读结果） | 无需改 dsh；但**要 skill 教**（AI 得记得用） | 立刻可做 |
| ❌ D. 纯 MCP 服务器推送 | —— | —— | 框架不支持 | 不可行 |

**结论**：**"完成事件"做得到**，只是必须由 **dsh 侧或 harness 的作业机制**承载，
而不是 MCP。建议顺序：**先 C（今天可用、零 dsh 改动）→ 再 A（最省，需确认 API）**。
C 与 A 共用同一个服务端入口（"阻塞到终态并返回摘要"），所以**先做那个入口**是共同前提。

### 4.2.1 成本模型（**用户明确要求"重点在效率"，按这个口径取舍**）

- 一次工具调用 ≈ **一次 HTTP 往返 + 回执进上下文**（几百 token 到几 KB）。
  ⇒ **调用次数比回执大小更重要**；能把 N 次轮询变成 1 次等待，就是纯赚。
- 一次**人肉转达**（"跑完了"）= 用户注意力 + 会话中断 ⇒ 最贵，优先消灭。
- 一次**假位置排查**（R25 那种）= 一小时（实测）⇒ 宁可多花一个字段也不许报假位置。
- 因此本设计的取舍：**默认摘要**（省回执）+ **长阻塞/链**（省次数）+
  **台账落盘**（省重复登记与"靠记忆对齐"）。

## 5. 提案：三层机制（详细设计见 `docs/设计-长任务编排与身份台账.md`）

一句话：**把"会话态"升级为「项目台账 + 调度器 + 契约化真相」**。

### L1 台账（`ml_mecha/ledger.py` 新增，落在 `.ml-mecha/ml_ledger/*.jsonl`）

- **dataset**：`fp = sha1(source 声明 ⊕ pipeline_id ⊕ 行数 ⊕ payload 声明 ⊕ 划分口径)[:12]`，
  `id = ds-<fp>`；**同数据同 id**（`reused: true`），名字降级为**别名** ← R32/R38
- **job**：稳定名 `job-<slug>-<n>`（`n` 持久）← R28
- **chain**：名 → 进度（步幂等键 = `hash(步参数 ⊕ dataset_fp ⊕ code_fp)`）← R33
- **run**：复用既有 `runs/`，**新增回显** `dataset_fp` / `pipeline_id` / `code_fp` ← R38
- **跨重启**：可复原的数据集（HDF5/CSV/帧文件）**懒复原**；内联 `arrays` 不可复原 ⇒
  明确回 `dataset_needs_reprepare` ← R32
- `describe_ledger()` = **run manifest 的视图**（不另造存储）← R38

### L2 调度器（挂在 `MLMecha.submit()` 这个唯一入口上）

- 超并发上限 ⇒ **入队**（回 `queue_position`），不再报错；`set_job_limit(n)` **热改** ← R29
- `read_job(句柄, wait="terminal", timeout_s≤540)`：**真等到终态**（客户端超时 ~10 min 内留余量）；
  超时回"还在跑 + 进度 + ETA"而**不是错误** ← R24/R35
- `wait_any(句柄们)`：谁先完谁先报 ← R24
- 句柄三种：`job_id` / **作业名** / `run_id` ← R28
- `submit_chain(steps, on_failure=stop|continue|retry(n))` + `resume_chain` ← R33/R40
- **完成事件**：按 §4 的 C → A 路径（不在 L2 里自己做推送）

### L3 契约与真相

- **投影约定**：一张 `LARGE_FIELDS` 清单（`ml_mecha/projection.py`）+ **判据遍历它**
  ⇒ 新增大字段不登记就红 ← R16/R18/R20/R21/R36（**终结"同一件事补三次"**）
- **终态不变量**：`run_id` 非空 **XOR** `error` 非空且 kind 具体；
  违反 ⇒ `silent_terminal`（框架自检失败） ← R26
- **资源一等化**：`estimate_run` 估算峰值显存 + 提交前预检（`cuda_oom_predicted`）
  + 运行期 `cuda_oom` 带数字；**毒化提示提到 message 首行** ← R25/R30
- **框架级分块**：`ctx["chunks"](budget_mb=…)`（**新增助手**，不动既有 `metrics` 契约）
  ⇒ 用户不再手写分块 ← R31
- **一次注册**：`custom_network` 装配时注册一次、代码按请求携带 ⇒ 竞态从根上消失 ← R27
- 顺带：verdict 文案明示"N 步内健康 ≠ N 步后健康" ← R34；
  交付说明标注"需重启 / 可热修" ← R37

**覆盖矩阵**（每条 R# → 机制 → 层）见设计文档 §6，此处不重复。

## 附：一句话总结给用户

> 40 条反馈不是 40 个功能，是**四个系统属性**（身份与持久 / 等待与编排 / 观测预算 /

> 交付"由**同一套**机制覆盖。唯一做不到的是"服务端主动唤醒 AI"——但那可以用
> **服务端自己把链跑完 + 一个阻塞到终态的入口**（今天就能用）替代，
> 更优的形态（插件注入会话消息）需要先确认 dsh 的注入 API（§4.3）。
