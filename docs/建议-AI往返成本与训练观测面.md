# 反馈：AI 在这个仓里的往返成本（来自一次真实工作的统计）

> **场景**：用 ML Toolbox 训练一个神经量子态（NQS）网络——GNN 图条件 + Transformer
> 自回归 + 复数概率幅输出头，真实里德堡阵列数据。本文统计的是**这次真实工作的过程**，
> 不是构造出来的例子。
>
> **与另一份反馈的关系**：`docs/反馈-NQS路径实测缺口.md` 记的是**功能**缺口
> （能不能做到）。本文记的是**效率**问题（做一次要花多少回合）——两者性质不同。
> ⚠ 那份文档里的缺口 4（负载形状无提示）**已经修好了**（见 §2），本文不再重复。

---

## 1. 一句话

**能力面已经够用了；真正卡住 AI 的是"每次失败都要一整个往返"。**
这次工作中，形状类错误我一个人犯了约 15 次，每次都花掉一个完整的
工具往返（提交 → 等 → 读错 → 改 → 再提交）。本地跑一次 python 是秒级，
所以我**被迫**采用"本地磨对形状、再提交一次"的策略——
这不是不信工具箱，是用最便宜的反馈回路把错误磨掉。

**如果只改一件事**：给 `run_custom` / `submit_run` 加 **`dry_run`**（§3 第 1 条）。
它能把这次的 ~15 次往返压到 2–3 次。

## 2. 先说好的：有一条已经明显变好了

## 3. 五条建议（按性价比排序）

### 建议 1【最高】给 `run_custom` / `submit_run` 加 `dry_run`

**现在没有**：我核实过工具面里 `dry_run` / `shape_check` / `precheck` /
`validate_code` **均为 0 处**。而 `run_custom` 的代码是**字符串**，
提交前我没有任何办法知道它跑不跑得起来。

**要什么**：一个只做三件事的开关——
1. `compile_network(code)`（**已经有了**这个函数，只是没接成命令）；
2. 用真实负载跑**一次** `forward_step`（**不反传、不落盘、不计入实验记录**）；
3. 回**每个中间张量的形状** + 首个异常的结构化归因。

**为什么这是最大的杠杆**：这次的形状错误，绝大多数**一次 forward 就能全部暴露**。
而现在的代价是每次一个往返。

**实测证据（本轮真实发生的形状错误，每条一个往返）**：

| 错误 | 报出来的话 | 根因 | dry_run 能不能一次抓到 |
|---|---|---|---|
| 负载维度塌陷 | `mat1 and mat2 shapes cannot be multiplied (2816x18 and 54x24)` | 我给 `(R,5)`，切批后变 2-D | ✅ |
| 设备不一致 | `Sizes of tensors must match except in dimension 2` / `not enough values to unpack` | `torch.tensor` 建在 CPU，模型在 cuda——**错误信息伪装成维度错** | ✅ |
| 形状覆盖 | `mat1 and mat2 shapes cannot be multiplied (12x6 and 12x16)` | `self.edge(node)` 在 4-D 上逐元素作用 | ✅ |
| gather 秩 | `Index tensor must have the same number of dimensions as input tensor` | 索引 `(10,6,1)` 对输入 `(1,10,6,2)` | ✅ |
| 维度混淆 | `Sizes of tensors must match except in dimension 2. Expected 1 but got 5` | 把 K（采样数）当成序列长度 L | ✅ |
| reshape | `shape '[6, 6, 2]' is invalid for input of size 120` | 写成 `(n*La, La, 2)`，应为 `(n*K, La, 2)` | ✅ |
| **批次相关**（本地测不出） | `Index tensor must have the same number of dimensions` | 本地 B=3、真实 B=2 ⇒ **只有 dry_run 用真数据才抓得到** | ✅（且只有它能抓） |

最后一行是重点：**我本地全绿、一提交就错**。原因是本地我用了自己的 batch 数，
真实负载的 batch 是 2。这类错误**只有"用真实负载做一次前向"才能发现**——
正是 dry_run 的定义。

---

### 建议 2【高】指标要能**多轮上报**（不只在 epoch 边界）

**现在**：`trainer.py` 里 `recorder.epoch(...)` 与 `metrics(...)` 都是
**每轮一次**（L514 / L526），`on_step` 是每步（L473）但**只回调、不能上报指标**。
于是"步"这一级**没有任何指标面**。

**这次的后果（很严重）**：我的 NLL 在**前 100 步内就崩到 0.0000**，
模型从此跑向近似均匀分布、保真度一直打不过"恒出均匀态"的基线。
但在 TensorBoard / `describe_training` 上，我只能看到**每轮**的值，
看不出它是**什么时候**崩的、崩得多快。**我是在本地脚本里逐轮打印才发现的**
（`--steps 600` 的那次快调，step 100 就显示 `nll 0.0002`）。

**要什么**：给一个"步级上报"的口子（例如 `on_step` 的返回值里允许带指标 dict，
或加 `metrics_every` 旋钮），这样 `describe_training` 就能给出步级曲线。

**为什么重要**：NQS 这类任务动辄 4500 步，**训练动态塌陷发生在前 2% 的步数里**。
只有 epoch 级观测 ⇒ AI 要到很晚才能发现，甚至发现不了。

---

### 建议 3【中】代码可从文件路径读（`code_path`）

**现在**：`run_custom` / `submit_run` 的代码是**字符串**。我这份网络源码约 9 KB。
调参（fid_w / lr / 各 warmup 步数）要跑 5 个组合 ⇒ **同一份代码发 5 遍**。

**要什么**：`code_path`（受已有 `dataset_roots` 管辖，不新增授权面）。
我改一行只改文件，不用把整份代码重发。

**顺带**：这也让"AI 写的网络源码"有了**仓内的单一存放点**，
`describe_network` 取回源码时也不会和文件版本分叉。

---

### 建议 4【中】`eval_custom`：自动继承训练负载 + 支持 `code_path`

**现在的现象**：`eval_custom` 的 `ctx["payload"]` **只含本次调用收到的负载**。
技能里"换一个没见过的 N 评估"的写法会直接 `KeyError: 'xr'`。
我最后是把负载**原样再传一遍**才评估上的。

**另外**（独立的一条 bug，上一份反馈也记过）：带 `dataset_id` 调用会崩
`AttributeError: 'dict' object has no attribute 'spec'`——
`ml_mecha/engine.py:957` 把 `check_dataset_ref()` 回的事实字典当成带 `.spec`
的对象用（`validator.py:515` 回的是 facts）。

**要什么**：默认继承训练时的负载；要换新数据时再显式覆盖。

---

### 建议 5【低】`metrics` 调用处包 `no_grad`

纯卫生问题：观测不该有梯度语义。现在我必须自己写 `with torch.no_grad():`，
否则全量负载上的保真度计算会建图、吃显存。
（上一份反馈的缺口 5，一并提一下。）

## 4. 一条与工具无关、但与"AI 用法"有关的自省

我该更早用 `reason` 参数。你开了这个接口之后，我前面若干轮**没写**，
导致在记录仪上，我那些"为定位形状错而做的探针调用"和"正式训练"
看起来是同一类东西。**写清 reason 之后，你能分辨"这是调试"还是"这是工作"**——
这对判断 AI 是否在浪费预算是关键的。以后我会一直写。
